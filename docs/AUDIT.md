# 子代理审计流程

记录每一轮「派子代理独立审查本仓库」的发现、判定与修复。

## 为什么要这样做

人（以及写代码的那个 agent）会对自己写的东西产生盲区。
本项目第 41 轮的真实教训：

> 连崩溃修了三轮，其中两次改错了指针。三次「修好了」，
> 用户三次反馈「还是挂了」。最后派两个子代理独立审查，
> 一次就找出了真正原因（`giveFocus(nullptr)` 是空操作，
> `currentFocus` 永久悬垂）。

**自己查自己不可靠。** 子代理不带前几轮的假设，只看代码。

## 流程

```
1. 派子代理（可并行），每个只负责一个角度
2. 子代理只诊断、不改代码，输出「文件:行号 → 问题 → 触发条件 → 严重程度」
3. 主代理逐条复核：是真的吗？能否复现？
4. 判定：已修 / 部分修 / 明确不修（附理由）/ 设计如此
5. 记录到本文件，包括「判为不修」的那些
```

### 派什么样的子代理

按**视角**分，不要按文件分。同一个文件被两个不同视角看，最容易出发现。

| 视角 | 提示词要点 |
| :--- | :--- |
| 内存安全 | 生命周期、裸指针、异步回调、析构顺序；要求给出触发时序 |
| 功能正确性 | 「用户点了之后真的有用吗」；要求实际跑一遍 |
| 平台移植 | 硬编码路径、桌面 GL 假设、缺失的驱动依赖 |
| 许可证合规 | 依赖链、分发义务、第三方声明是否与实际一致 |
| 文档一致 | 文档承诺 vs 代码行为，逐条对照 |

### 提示词必须包含的约束

- 明确给出仓库路径与构建方式
- 要求**只诊断不改代码**（避免并行冲突）
- 要求每条结论附代码位置或实测证据，不接受「可能有问题」
- 要求区分「实测复现」与「静态推导」——这两者的可信度差一个数量级
- 允许它跑测试、写临时程序验证假设

## 判定标准

| 判定 | 含义 |
| :--- | :--- |
| **已修** | 改完了，且有验证方式证明改前会失败 |
| **部分修** | 修了主要部分，其余明确不修并说明原因 |
| **不修（明确）** | 承认问题存在，但权衡后不改，必须写理由 |
| **设计如此** | 不是缺陷，是刻意选择，写清为什么 |

**「部分修」「不修」必须记录下来。** 只记「已修」会让下一个人重新发现同样的问题。

## 记录格式

```markdown
## 第 N 轮（日期，版本）

**参与子代理**：N 个，视角分别是 …

### 发现

#### 1. <一句话结论>

- **位置**：`path/to/file.cpp:123`
- **证据**：实测复现 / 静态推导
- **触发条件**：…
- **严重程度**：会崩 / 可能崩 / 行为错误 / 优化
- **判定**：已修 / 部分修 / 不修 / 设计如此
- **说明**：为什么这样判定
```

## 第 1 轮（2026-10-29）

**参与子代理**：2 个
- 内存安全（点击崩溃根因）
- 界面层野指针（`src/` 全量审查）

### 发现

#### 1. `giveFocus(nullptr)` 是空操作，`currentFocus` 永久悬垂

- **位置**：`external/borealis/library/lib/core/application.cpp:929`
- **证据**：实测——用独立程序复刻该逻辑，`giveFocus(nullptr)` 后
  `currentFocus` 仍指向旧地址
- **触发条件**：焦点所在的 View 被销毁（切标签、pop Activity）
- **严重程度**：会崩
- **判定**：**已修**
- **说明**：赋值被关在 `newFocus != nullptr` 分支里，导致
  `View::~View()` 的焦点自查是死代码。同时 `oldFocus` 解引用前没有
  存活检查，配套修了 `frame()` 与 `popActivity()` 的两处裸解引用。

#### 2. 标签索引越界导致 `Sidebar::getItem` 返回野指针

- **位置**：`external/borealis/library/lib/views/sidebar.cpp:185`
- **证据**：实测——`MUVIK_START_TAB=1000` 连跑必崩
- **触发条件**：任何把越界索引传给 `TabFrame::selectTab`
- **严重程度**：会崩
- **判定**：**已修**（项目侧夹紧索引，不改上游）
- **说明**：`contentBox->getChildren()[position]` 没有边界检查，
  越界后 `dynamic_cast` 在野指针上取 `type_info` 直接 SEGV。

#### 3. `NowPlayingBar::instance_` 从不置空

- **位置**：`include/view/now_playing_bar.hpp:31`
- **证据**：静态推导（代码依据充分）
- **触发条件**：Activity 销毁后 `AudioPlayer` 的状态回调仍会周期性触发
- **严重程度**：会崩
- **判定**：**已修**
- **说明**：`static inline` 单例指针没有在析构时清零，
  音频回调里的 `NowPlayingBar::get()->refresh()` 会写已释放内存。

#### 4. 触摸复用野指针（按住期间界面重建）

- **位置**：`external/borealis/library/lib/core/application.cpp` `processInput`
- **证据**：实测——ASan 报 `heap-use-after-free`，加守卫后 rc 从 134 变 0
- **触发条件**：手指按住列表项期间，扫描完成触发 `clearViews()`
- **严重程度**：会崩
- **判定**：**已修**

#### 5. `PluginManager::plugins_` 无锁

- **位置**：`src/plugin/plugin_manager.cpp`
- **证据**：静态推导——`#include <mutex>` 存在但零 `lock_guard`
- **触发条件**：插件管理页卸载/重扫时，插件浏览页正在遍历
- **严重程度**：可能崩（use-after-dlclose）
- **判定**：**已修**

#### 6. `library_list_` 不回读 slot

- **位置**：`src/activity/file_browser_activity.cpp:467`
- **证据**：静态推导——`sources_container_` 有回读，`library_list_` 没有
- **严重程度**：可能崩
- **判定**：**已修**

#### 7. `openForText` 回调捕获 `this` 无存活检查

- **位置**：`src/activity/plugin_manager_activity.cpp:93,188,210,232`、
  `src/activity/file_picker_activity.cpp` 的手动输入路径（原 `folder_picker_activity.cpp`）
- **证据**：静态推导
- **触发条件**：打开输入框后按 B 返回，再提交
- **严重程度**：可能崩
- **判定**：**未修**
- **说明**：这些路径需要「Activity 已 pop 但 IME 对话框仍存活」。
  当前 UI 流程下 IME 是模态的，Activity 不会先被销毁。
  没有实测复现，暂不改动——避免在没有证据的情况下引入新问题。
  **若将来出现相关崩溃，这里是第一嫌疑。**

### 本轮修正的教训

- 前两次修复都检查 `view`（手势所属 View），但崩溃发生在 `currentFocus`
  （全局焦点）上。**同一个函数里有多个指针时，要逐个确认崩溃的是哪个。**
- 「没崩了」不等于「修好了」：第 41 轮的冒烟测试证明，
  崩溃消失后功能仍然是坏的（点击无反应）。

## 如何发起一轮审计

子代理不共享本会话的上下文，提示词必须自包含。模板：

```
仓库：/Users/yiuf/code/muvik（C++17，Borealis UI + libmpv）

背景：<这次改了什么，已知哪些问题>

你的任务：只审查 <某个角度>，不要改任何文件。

要求：
1. 每条结论给出 `文件:行号`
2. 明确区分「实测复现」与「静态推导」
3. 不接受「可能有问题」这类无依据的说法
4. 输出表格：位置 | 问题 | 触发条件 | 严重程度

可以运行命令、读文件、写临时程序验证假设。
如需临时改动来验证，改完必须还原并在报告里说明。
```

**并行派多个子代理时，务必让它们都不改文件**，否则会互相覆盖。
